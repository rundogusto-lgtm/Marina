День 1. Выбор темы, обоснование актуальности, инструменты реализации
«Старый Бердск» — веб-система управления арендой объектов парка отдыха
Цель проекта: разработать веб-приложение для автоматизации процессов бронирования и управления арендой беседок, мест под палатки и парковочных мест в парке отдыха «Старый Бердск», а также для информационной поддержки посетителей и аналитической поддержки директора.
Обоснование актуальности
Тематика цифровизации парков отдыха и зон рекреации в 2025–2026 годах является практически значимой по нескольким причинам.
Автоматизация бронирования снижает нагрузку на персонал и повышает качество сервиса. Традиционные бумажные и телефонные процессы бронирования в сфере аренды пространств создают очереди, ошибки и потери заявок. Веб-системы с интерактивной картой и онлайн-расписанием позволяют клиенту самостоятельно выбрать и забронировать объект, что снижает административные расходы и повышает удовлетворённость. Для парков, где арендуются беседки и места под палатки, это особенно актуально из-за сезонного пика спроса.
Интерактивная карта с визуализацией занятости решает проблему навигации. Клиент, который видит на карте свободные объекты с ценами и может сразу забронировать, тратит меньше времени и реже уходит к конкурентам.
Аналитика для директора превращает данные в управленческие решения. Встроенные системы аналитики в системах управления арендой дают владельцам и управляющим полезные инсайты для принятия решений на основе данных. Для директора парка это означает: видеть загрузку объектов, выручку по категориям, сравнивать периоды и вовремя реагировать на аномалии.
Роль администратора с обходом территории и актуализацией данных закрывает разрыв между онлайн-бронированием и физической реальностью парка. Пока клиент бронирует онлайн, кто-то должен подтвердить заезд, отметить выезд и актуализировать статус объекта. Отдельная вкладка для обхода территории решает эту задачу без необходимости сложных интеграций.
Печать чеков с подписью директора — практическая необходимость для легитимности расчётов. Согласно требованиям к документам, подтверждающим оплату, документ должен содержать наименование, номер, дату, наименование услуги, сумму, должность и подпись выдавшего лица. Система, которая автоматически формирует такой документ в формате А4 для подписи директора, снижает риск ошибок и ускоряет расчёты.

2. MVP (Фаза 1)
2.1 Интерактивная карта парка
    • Схема парка: скриншот 2ГИС + SVG-квадратики объектов.
    • Три типа объектов с визуальным различением:
        ◦ Беседки — номер, вместимость, цена за час/день.
        ◦ Места под палатки — зона, площадь, цена за сутки.
        ◦ Парковочные места — номер, тип автомобиля, цена за час/день.
    • Цветовая индикация статуса: зелёный — свободно, красный — занято, серый — недоступно (ремонт/техобслуживание).
    • Фильтры: по типу объекта, по дате, по времени, по вместимости.
    • Клик по объекту открывает карточку с описанием, фотографией, ценой и доступными слотами.
2.2 Процесс бронирования (оплата на месте)
    1. Клиент выбирает дату и время.
    2. Карта отображает только свободные объекты.
    3. Клиент выбирает объект, указывает длительность аренды.
    4. Система рассчитывает стоимость и формирует заявку.
    5. Оплата производится на месте; статус брони — «Ожидает оплаты».
    6. Администратор подтверждает оплату, статус меняется на «Оплачено».
2.3 Панель администратора
    • Список всех броней с фильтрами: дата, статус (новая / подтверждена / активна / завершена / отменена), объект, клиент.
    • Подтверждение оплаты, отмена и перенос брони.
    • Отметки «Заезд» и «Выезд».
2.4 Простой дашборд директора
    • Выручка за сегодня / неделю / месяц (с разбивкой по типам объектов).
    • Процент загрузки беседок, палаток, парковки.
2.5 Печать чека (формат А4, для подписи)
Система генерирует документ, содержащий:
    • Наименование документа и порядковый номер.
    • Дату и место расчёта.
    • Наименование организации и ИНН.
    • Наименование услуги, количество, цену за единицу и сумму.
    • Количество людей и количество машин (по данным брони).
    • ФИО и должность лица, выдавшего документ.
    • Место для подписи директора.
Документ печатается на обычном принтере, затем подписывается директором — это придаёт ему юридическую силу.
3. Формальные требования
3.1 Функциональные требования
    • Клиент может забронировать беседку на выбранную дату.
    • Администратор может подтвердить оплату брони.
    • Директор может распечатать чек формата А4.
    • Система отображает занятые объекты красным цветом.
    • Карта показывает три типа объектов: беседки, палатки, парковки.
3.2 Нефункциональные требования
    • Карта загружается за 2 секунды.
    • Данные сохраняются между сессиями (localStorage).
    • Интерфейс работает на экранах от 320px.
    • localStorage не превышает 5 MB.
    • Система работает без сервера (только статика).
4. Фаза 2 (после MVP)
    • Доска объявлений: категории (Новости, Акции, Мероприятия, Важные уведомления), публикация текста, изображений, PDF.
    • Отзывы клиентов после завершения аренды.
    • Напоминания клиенту за день до брони.
    • Вкладка «Обход территории» для администратора.
    • Журнал действий: кто, когда, что изменил.
    • Расширенный дашборд: средний чек, топ-5 объектов, график загрузки по часам, новые брони vs отмены.
    • Отчёты с экспортом в Excel/PDF: по выручке, загрузке, клиентам, отменам, сменам, сравнение периодов.
    • Управление ценами и акциями: сезонные коэффициенты, промокоды, «часы пик».
    • Уведомления о низкой загрузке и аномалиях.

6. Диаграммы
6.1 Use Case
    • Клиент: просмотр карты → выбор объекта → выбор даты/времени → подтверждение брони → просмотр статуса.
    • Администратор: просмотр броней → подтверждение оплаты → отметка заезда/выезда.
    • Директор: просмотр дашборда → печать чека → просмотр отчётов.
6.2 Последовательность бронирования
    1. Клиент кликает по объекту на карте.
    2. Система проверяет доступность в localStorage.
    3. Клиент выбирает дату/время.
    4. Система рассчитывает цену.
    5. Бронь сохраняется в localStorage со статусом «pending».
    6. Карта обновляется — объект становится красным.
6.3 Компоненты
Карта (SVG), модуль бронирования, модуль администратора, модуль директора, хранилище (localStorage).
7. Тесты
Unit-тесты (Vitest):
    • calcPrice(objectId, hours, date) — расчёт стоимости с сезонным коэффициентом.
    • isSlotAvailable(objectId, date, time) — проверка, что слот не занят.
    • formatReceipt(booking) — проверка полей чека (номер, дата, объект, сумма).
    • getObjectStatus(objectId, date) — проверка цветовой индикации.

ТЕХНИЧЕСКОЕ ЗАДАНИЕ
на практическое занятие № 9 по МДК.02.01 «Технология разработки программного обеспечения»
Тема: Разработка тестового сценария. Оценка необходимого количества тестов.
Цель работы: научиться разрабатывать тестовые сценарии (тест-кейсы) для заданной функции программного обеспечения, применяя методы эквивалентных классов и граничных значений, а также обосновывать необходимое количество тестов.
Проект: «Старый Бердск» — веб-система управления арендой объектов парка отдыха.
Выбранная функция: бронирование беседки на выбранную дату и время (с расчётом стоимости).
1. Требования к функции
    1. Требование 1. Клиент может забронировать беседку только на дату, которая ещё не прошла и не превышает 90 дней вперёд от текущей даты.
    2. Требование 2. Длительность аренды беседки должна быть от 1 до 12 часов включительно.
    3. Требование 3. Количество гостей не должно превышать вместимость выбранной беседки и не может быть меньше 1.
    4. Требование 4. Количество автомобилей не может быть отрицательным и не должно превышать вместимость парковки (для парковочных мест — от 1 до 5).
    5. Требование 5. Бронь не может быть создана, если выбранный временной слот уже занят другой активной бронью.
2. Входные параметры функции
    • date — дата бронирования.
    • hours — длительность аренды в часах.
    • guests — количество гостей.
    • cars — количество автомобилей.
    • objectId + timeSlot — выбранный объект и временной слот.

6. Обоснование количества тестов
Выбрано 7 тест-кейсов, потому что:
    • TC-01 покрывает все валидные классы одновременно — проверяет успешный сценарий.
    • TC-02 проверяет невалидный класс по дате (прошлое).
    • TC-03 проверяет нижнюю границу по часам (1 час — ровно на границе).
    • TC-04 проверяет верхнюю границу по часам (13 — после границы 12).
    • TC-05 проверяет верхнюю границу по гостям (9 — после границы 8).
    • TC-06 проверяет нижнюю границу по машинам (-1 — до границы 0).
    • TC-07 проверяет невалидный класс по занятости слота.
Что покрыто:
    • Все валидные классы (TC-01).
    • Все невалидные классы (TC-02, TC-04, TC-05, TC-06, TC-07).
    • Границы: hours (1 и 12), guests (8), cars (0).
    • Не покрыты: граница date +90 дней и граница guests = 1. При необходимости можно добавить TC-08 (date = +91 день) и TC-09 (guests = 0), но для учебной работы 7 тестов достаточно, чтобы показать применение методов эквивалентных классов и граничных значений.
7. Вывод
В ходе работы разработан тестовый сценарий для функции бронирования беседки в веб-системе «Старый Бердск». Сформулировано 5 требований, выделены эквивалентные классы и граничные значения для пяти входных параметров, составлено 7 тест-кейсов, покрывающих положительные и отрицательные сценарии. Обосновано количество тестов: выбранный набор покрывает все валидные и невалидные классы, а также ключевые границы по часам, гостям и машинам. Методы эквивалентных классов и граничных значений применены корректно, что позволяет эффективно проверить функцию без избыточного количества тестов.
